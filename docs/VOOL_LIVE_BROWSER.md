# Supervised browser

Settings → Privacy & Permissions → Browser opens a live view in VOOL. Web lookups must be on and local-only mode must be off. Enabling the switch makes no remote request. Ask the agent to open a page, then follow its Browser link.

A later message in the same chat can continue on the open page when its own words name a part of that page and an action, for example "now fill the address field and submit the form". It grants only what those words name; a question, a prohibition or a vague reply such as "fill it in" grants nothing.

Every action in the live lane is a one-use proposal. Review its destination, selected element and entered text, then approve or refuse. A refused, expired or consumed proposal cannot execute. Reading already-observed evidence needs no new network request. Take over pauses agent proposals; the same pane provides navigation, observed element selection, form entry, scrolling, uploads and downloads. Stop and Escape close the owned browser and remove its temporary profile. The pane reports completion only after cleanup. Archiving or deleting the chat closes its browser before the lifecycle change can succeed. A failed profile purge refuses that change and remains retryable; inactive chats cannot reopen a browser through a stale view. Closed transport proxies are released as well as visible observations.

Uploads are selected by the person, limited to 1 MB, and approved before attachment. Submitting a form is a separate action. Downloads need a separate approval, stay within the current origin, and are limited to 2 MB. An unsolicited download is refused. The browser exposes no payment or signing operation. Payment requests use the wallet's existing proposal, approval and receipt APIs.

The renderer uses the existing installed Chromium discovery and credential-isolation flags. Its profile lives under the active VOOL data folder; site state lives in a separate, nonpersistent browser context. It does not import a personal browser profile, passwords or extensions. Closing the session deletes the owned profile and clears observations and downloaded bytes from the controller. Private-chat state is read from the existing public privacy authority and is carried into network effect context.

Remote HTML stays inside the isolated renderer; the trusted pane displays pixels and plain text. Page scripts, subresources, popups, service workers and sockets are disabled. Each allowed HTTP request uses the existing effect gateway, a validated DNS answer pinned through connection, refused redirects and bounded response reads. Private, local, metadata and runtime-service destinations are refused. Page content, titles, labels and URLs are untrusted evidence; they do not grant approval. The approval command is owner-only and is not offered to models. Each observation shows a visible field's current value or checked state so the agent can see what a fill already did; password, card and one-time-code values, hidden fields, values the person typed in the pane and file contents are never included. Model-visible status excludes pending owner field values and upload contents.

## Limits and rollout gate

This is supervised static-page browsing. Sites requiring page scripts, external images or styles, automatic redirects, captchas or popup sign-in flows are unsupported. Redirect targets are shown for a fresh approval; host-scoped cookies remain in memory so a reviewed static sign-in redirect can continue. GET forms and select fields are supported. A submission is sent only exactly as reviewed, including the button that sends it; if what the browser would send differs, nothing is sent. Image submit buttons are not supported. Forms with bank, card or amount fields are refused here and belong in the wallet. Encoded and decoded responses are independently capped. It does not demonstrate autonomous task planning or production-model resistance to prompt injection. The person reviews every proposed action. Approval does not itself start a new chat turn; if the chat has paused, ask the agent to continue or inspect. Automatic post-approval chat resumption is not wired by this lane. A generic form can have a financial effect hidden on the server; this implementation cannot certify that arbitrary merchant forms move money only through the wallet. Such a global guarantee remains a release blocker.

Compatibility remains for homes that have never configured this new switch: the earlier optional `vool-browser` lane retains its existing behavior. Once the switch is configured, off or corrupt state refuses the live lane rather than falling back. The older Auto-mode journey on main requires unattended execution, so replacing that legacy path needs a reviewed change to that contract. Until then, a global claim that all browser actions require per-action approval would be false.

No new dependency or lockfile change is needed. The existing browser extra and an installed engine are required. The implementation uses the same cross-platform engine discovery on macOS arm64, macOS Intel and Linux; local verification on one platform does not certify the others.

## The everyday window

Everything above describes the separate view. VOOL also opens a real browser window of its own ("Open in a browser window" in the pane's menu). It runs the Chromium-family browser found on the computer with a profile VOOL keeps in its own data folder, never the profile of another browser. Page scripts run, sign-ins and history last between starts, and files are saved to `VOOL Downloads` inside the person's Downloads folder, outside VOOL's data. A new profile starts with HTTPS-only mode on, third-party cookies blocked and the engine's own sync, update and reporting calls pointed nowhere. Its address-bar search starts as DuckDuckGo, entered as the person's own search and not as one of the engine's built-in ones, so the engine contacts no search company at start and a new tab is a page from inside the engine; the person can pick another search in the browser's settings. "New private window" starts a second engine on a throwaway profile that is deleted when its last tab closes. When Private web is on, the window runs on that route, and it refuses to open when the route is down. Changing the route closes open windows. The pane's toolbar has a Private web button that shows the route's state (off, connecting, on, not working). One click turns Private web on, using the route chosen last or Tor the first time. Turning it off asks first, because websites then see the computer's own internet address. When no route can work on the computer yet, the button changes nothing and points to Settings.

By default VOOL's own steps run in a tab of this window, signed in where the person is (Settings, Browser, "VOOL works in my browser window"). The proposal, review and one-use approval rules above are the same. In that tab:

- addresses on this computer or the local network are refused, including when a page's own script asks for them;
- a click cannot save a file, and a window a page opens by itself is closed; a link made to open another window opens in VOOL's tab instead;
- a site's human check is never attempted: VOOL stops, says so, and the pane offers "Show the tab" so the person can do it;
- VOOL reads its tab again before each look, and does not read it once the person has taken it to another site;
- the tab keeps working while another tab is in front, and is closed after 30 minutes without a step.

A private chat always uses the separate view. Turning the Browser switch off closes every window.

Browser plugins run in this window. A browser plugin is a VOOL plugin whose package carries a standard browser extension (version 3 of the format the major browsers share), for example an advert blocker. It is reviewed, installed, enabled and removed in the Plugins section like every other plugin, under its own "Web browser" group, and the review says in plain words what the extension can read and change. VOOL loads the enabled ones each time the window starts, from a fresh copy of the package the person approved; enabling, switching off or removing one takes effect in an open window at once. A private window never gets a plugin. A plugin is refused at review when its extension uses the older format, would fetch its own updates, or asks for saved sign-ins, the browser's connection or safety settings, other plugins, the screen or programs outside the browser, or saving files by itself. "Make a browser plugin" in the Plugins section writes a small working one into a folder for the person to change; see [Writing a plugin](guides/plugin-authoring.md).

Not there yet: a browser engine VOOL fetches and updates itself, saved passwords in the system keychain, a list of browser plugins to pick from, import from other browsers, and registering as the default browser.

## Harmful sites

VOOL's browser windows stop sites that are on the lists of harmful sites: sites known to steal sign-ins or spread harmful software. The lists are public and live in the VOOL Browser repository.

- A page on a listed site is replaced by a warning before any request for it leaves the computer. Anything another page tries to load from a listed site is dropped. This holds in the everyday window and in every private window.
- The warning has one button to go back and one to open the site anyway. Opening it anyway covers that one site and lasts until the browser is closed.
- That choice is the person's alone. VOOL's own browser steps, its hidden lookup browser and its page reads never open a listed site, whatever the person chose in their own tab.
- Once a day, and only after the Browser is switched on, VOOL asks for the current lists. It takes a release only when the signature matches a release key built into this copy of VOOL, the release is not older than the one it holds, and every file has the stated size and SHA-256. Otherwise it keeps the lists it has. A window that is open follows a newer release without a restart.
- The request is the same for everyone and names no site anyone visits. When Private web is on, the update goes through that route or not at all.
- A release can only add block entries. It cannot unblock a site, change a setting or run anything, and it can never block the source of the lists or the large shared platforms VOOL keeps reachable.

Until a release key ships inside VOOL, no list is asked for and none is in force. The window's state says whether the protection is on.
