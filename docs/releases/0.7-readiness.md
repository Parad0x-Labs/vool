# Preparing VOOL 0.7

This is a release plan, **not an announcement of a shipped 0.7**. The runtime and
package remain at 0.6 until the memory/context candidate is reviewed and integrated.
The current distribution status remains in [Release status](../trust/release-status.md).

## Required release gates

| Gate | Required evidence before publication |
| --- | --- |
| Memory/context update | Reviewed commit included in the release source; working ingestion, retrieval, context assembly, correction/forgetting and isolation flows; cumulative regression and recorded latency/resource measurements. Do not advertise benchmark gains that were not measured. |
| Other pending changes | Reconcile the integration queue, including security and cross-tab state fixes. Freeze one source commit after integration; rebuild from it. |
| Version identity | Update `core/app_version.py`, `pyproject.toml` and `config/release/update_channel.json` together, run their contract tests, and record the exact source in every build manifest. |
| Linux | Run the ordinary Linux CI shards **and** `Linux desktop acceptance` on Ubuntu 22.04 and 24.04. The desktop check opens the real GTK/WebKitGTK chat, edits its composer and verifies owned runtime shutdown. An unrun workflow is not a pass. |
| Mac Apple Silicon | Build `--self-contained --arch arm64`; pass the whole-bundle CPU, deployment, dependency and immutability checks; launch the exact artifact on supported hardware. |
| Mac Intel | Build a separate `--self-contained --arch x86_64` artifact. A translated cross-build is labelled non-native evidence and still requires testing on a real Intel Mac. Do not offer the arm64 download to Intel users. |
| Upgrade | Test an existing 0.6 profile through restart and upgrade without losing saved credentials, chats, wallet references or permissions. Memory schema migration needs recovery evidence. Never use an owner's profile as a disposable test fixture. |
| Downloads | Every platform has a named download on the GitHub release and the website: `VOOL-<version>-macos-arm64.dmg`, `VOOL-<version>-macos-x86_64.dmg` (`--release-dir` or `--release-sign`), `vool-<version>-source.tar.gz` for Linux, the Windows installer, each with a published SHA-256 (`release_sign checksums` or `seal`). Unsigned downloads carry the first-open steps beside the link. |
| Signing | Opt-in for 0.7 (owner, 2026-10-06): certificates follow the release. When credentials exist, macOS uses `--release-sign` and the directory is sealed; see [Signed releases](#signed-releases). |
| Distribution | Publish matching artifact names, signed checksums, source/build manifests and OS/CPU labels on both website and GitHub channels. Review the actual update-feed state; do not imply it exists merely because the code supports it. |

Private candidates, local capture data, credentials and machine-specific paths are
excluded from public source and release inputs. Publication belongs to the release
owner after these gates; this preparation does not publish or deploy anything.

## Linux install and desktop behavior

The supported Linux route is currently **installation from source**, not a
self-contained AppImage or DEB. The bootstrap downloads the public `vool` repository;
the installation directory retains its existing `vool-local` name for compatibility.

The installer puts VOOL and Stop VOOL into the application menu under
`$XDG_DATA_HOME/applications` (normally `~/.local/share/applications`). If a Desktop
folder exists, it also creates matching desktop shortcuts. Neither requires root.
The standard Open Chat shortcut opens the served chat in the system browser.
Runtime keep-alive uses the existing user systemd service, with XDG autostart fallback.

The native-window lane additionally needs pywebview and Linux GUI libraries.
For the GTK lane on the tested Ubuntu targets, the acceptance workflow provisions
`python3-gi`, `python3-gi-cairo` and `gir1.2-webkit2-4.1`, with a Python environment
that can import those system bindings. A headless machine uses the server/browser
route; it is not reported as a native desktop launch. See the
[pywebview installation guide](https://pywebview.flowrl.com/guide/installation).

Linux release packages are a separate delivery gate: choose and verify the intended
format and supported CPU architectures before advertising a packaged download.

## Intel and older Macs

An Intel 2020 MacBook Pro is not inherently too old for VOOL. **CPU architecture,
macOS version and model resources are separate checks.** An ARM64-only Python cannot
run on Intel; Rosetta does not translate ARM executables into Intel executables.

The current self-contained bundle has a macOS 14 minimum. Its bundled Ollama and
native dependencies must pass the deployment census at that minimum. Lowering
`LSMinimumSystemVersion` alone does not add support for macOS 12 or 13.

Before considering an older-OS build, record the actual failing Mac's `uname -m`,
`sw_vers -productVersion`, exact error, artifact checksum and build manifest. If the
OS is supported but the download is ARM64, deliver the Intel build. If the OS is
below the declared floor, rebuilding/replacing dependencies needs its own budgeted
compatibility pass and real target-machine acceptance.

The packaged shell launcher now checks architecture and minimum OS before starting
embedded Python. A mismatch produces an actionable alert and an app-log entry,
rather than proceeding into a `Bad CPU type` failure.

Intel source installs used to fail at dependency resolution: PyTorch has published no
Intel macOS wheel since 2.3. The dependency declarations now skip torch and its dependents
on Intel macOS (LoRA training reports itself unavailable there). `cryptography` keeps its
`>=50.0.0` floor on every platform; the Intel bundle uses the 50.0.2 wheel recorded in
`installer/bundle/built_wheels.json`.

For an 8 GB machine, test the cloud-model path first. Running a large local model is
a different resource requirement from opening the app. Record startup time, idle
RAM and chat responsiveness on the target device before making performance claims.

## Release sequence

1. Land reviewed memory and remaining queue changes; freeze the source commit.
2. Set the 0.7 version in all authorities and run the cumulative gates above.
3. Build each named platform artifact from that exact clean commit, macOS with
   `--release-dir` (or `--release-sign` once credentials exist).
4. Run target-hardware and upgrade acceptance on those exact artifacts.
5. Write checksums (`release_sign checksums`), or seal and verify when a release key exists.
6. Publish consistent downloads and release notes containing measured changes and
   explicit remaining limitations.

## Signed releases

Signing is opt-in for 0.7 and becomes the default once the certificates exist. A signed
release opens on macOS without a Gatekeeper warning, and Linux users can prove the download
came from the VOOL release key. Signing keys,
certificates and notary credentials stay with the release owner: never in this
repository, in build logs or in task folders. Both tools fail closed: with a credential
missing they sign nothing, and a failure part-way leaves no half-signed artifact.

**macOS.** `installer/bundle/build_macos_app.sh --self-contained --arch <arch>
--release-sign <release-dir>` checks the credentials before the build starts, then
`installer/bundle/sign_macos_release.sh` signs every Mach-O file inside out with the
Developer ID Application identity, the hardened runtime and a secure timestamp
(entitlements in `installer/bundle/VOOL.entitlements`, applied only to the embedded
interpreter and the app), verifies the Team ID on every file, notarizes and staples the
app, builds the DMG from it, then signs, notarizes and staples the DMG. It writes
`VOOL-<version>-macos-<arch>.dmg` and a `.signing.json` receipt. `--release-dir <dir>`
writes the same name ad-hoc signed and not notarized; every Mach-O in it must carry a valid
signature or the build fails, because Apple Silicon will not run unsigned code. On first
open, macOS 15 and later need System Settings > Privacy & Security > **Open Anyway**
(right-click > Open no longer bypasses Gatekeeper there).

| Environment variable | Holds |
| --- | --- |
| `VOOL_MACOS_SIGN_IDENTITY` | The Developer ID Application identity name or its SHA-1 hash, as `security find-identity -v -p codesigning` lists it |
| `VOOL_MACOS_TEAM_ID` | The 10-character Apple Team ID every signature must carry |
| `VOOL_NOTARY_PROFILE` | A `xcrun notarytool store-credentials` keychain profile name |
| `VOOL_NOTARY_KEY_FILE`, `VOOL_NOTARY_KEY_ID`, `VOOL_NOTARY_ISSUER` | Instead of a profile: an App Store Connect API key file outside the repository, its key id and issuer id |
| `VOOL_SIGN_KEYCHAIN` | Optional: a dedicated keychain holding the identity |

**Linux and the whole release.** Linux installs from source, so its release artifact is
the source archive: `python -m installer.release_sign source --ref v<version> --version
<version> --out <release-dir>`. Then `python -m installer.release_sign seal --dir
<release-dir>` signs every file in the directory with GnuPG (OpenPGP): a detached
`<file>.asc` per artifact plus `SHA256SUMS` and `SHA256SUMS.asc`. It refuses a DMG
without its notarization receipt or whose bytes changed since notarization, and on macOS
re-checks the staple and Gatekeeper live; `--allow-unnotarized` seals ad-hoc DMGs instead.
Without a key, `python -m installer.release_sign checksums --dir <release-dir>` writes
`SHA256SUMS` and a `.sha256` sidecar per file, signing nothing. The key is named by full fingerprint in
`VOOL_RELEASE_GPG_KEY` and must belong to the public key pinned at
`config/release/release-signing-key.asc`; with no pinned key nothing is sealed. After
signing, everything is verified against the pinned key alone, the way a user verifies it.
OpenPGP is used because `gpg` ships with every mainstream Linux distribution, so users
verify without installing anything, and the same key can later sign an APT repository
or AppImage.

Users verify a download with:

```bash
gpg --import release-signing-key.asc        # once; compare the fingerprint with the website
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

Windows Authenticode signing is not part of this tooling; the Windows installer is built
elsewhere and, while unsigned, opens through SmartScreen's **More info > Run anyway**.
