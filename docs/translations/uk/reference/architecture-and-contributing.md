# Архітектура та участь у розробці

## Архітектура на одній сторінці

VOOL — це настільне середовище виконання, що працює насамперед локально, з ядром у вигляді локального сервера:

```text
┌──────────────────────────────────────────────┐
│ Native window / browser console              │
│  (served pages; the console you use)         │
├──────────────────────────────────────────────┤
│ Served runtime (local HTTP API)              │
│  routing → tool execution → answers          │
├───────────────┬──────────────┬───────────────┤
│ Local models  │ Cloud lanes  │ Wallet (opt)  │
│ (Ollama etc.) │ (your keys)  │ pilot lanes   │
├───────────────┴──────────────┴───────────────┤
│ Records: receipts, ledgers, fault registry   │
│ Local storage (SQLite under your profile)    │
└──────────────────────────────────────────────┘
```

Принципи, які забезпечує код:

* **Локально за замовчуванням; хмара — за вашим ключем.** Хмарні напрями існують лише з вашими обліковими даними й
  вашими стелями.
* **Один власник у кожного рішення.** Дозволи, витрати й вихідний мережевий трафік мають по одному
  контракту-власнику; збої класифікуються на тій межі, яка ними володіє.
* **Казати, що не вдалося.** Невідомі результати позначаються як невідомі; відмови кажуть, що не
  відбулося; закріплену модель ніколи не підмінюють мовчки.
* **Усе записується.** Виклики інструментів, схвалення, платежі й оновлення створюють квитанції у
  вашому профілі.

## Налаштування середовища розробки

```bash
git clone https://github.com/Parad0x-Labs/vool.git
cd vool
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest tests -q            # the suite
```

Нотатки щодо платформ, повна структура інструментарію й перевірки перед випуском містяться в
інженерній документації репозиторію (`docs/` у корені репозиторію; глибокі внутрішні подробиці не входять до цього публічного
сайту документації).

## Документація: одне канонічне джерело

Цю документацію створено з **одного** джерела — папки `docs/` цього репозиторію (структура
GitBook, `.gitbook.yaml` у корені репозиторію). З неї збирається публічний сайт документації. Щоб працювати з документацією:

```bash
python3 tools/docs/build_docs.py --src . --out docs-build --base /docs
python3 tools/docs/check_docs_build.py docs-build /docs
python3 -m http.server -d docs-build 8000   # local preview
```

Довідник помилок (`ERROR_BOOK.md`) і маніфест передачі на локалізацію
**генеруються з власних реєстрів середовища виконання** — генеруйте їх заново й ніколи не редагуйте вручну:

```bash
python -m tools.generate_error_book
python -m tools.generate_localization_handoff
```

Окремий тест провалює збірку, якщо згенеровані файли розходяться зі своїми реєстрами.

## Участь у розробці

* Невеликі зміни з рецензуванням; кожне твердження в документації має відповідати коду в тому вигляді, у якому його випущено.
* Зберігайте стабільні коди й ідентифікатори — вони живуть довше за збірки.
* Ніколи не розширюйте повноважень мовчки: новий дозвіл, новий шлях витрат чи новий напрям вихідного трафіку — це зміна
  архітектури, а не латка.
* Обмеження бета-версії документуються, а не приховуються — якщо ви знайшли незадокументоване обмеження, це
  помилка в документації.
