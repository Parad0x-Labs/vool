# Архитектура и участие в разработке

## Архитектура на одной странице

VOOL — это настольная среда выполнения, работающая прежде всего локально, с ядром в виде локального сервера:

```text
┌──────────────────────────────────────────────┐
│ Native window / browser console              │
│  (served pages; the console you use)         │
├──────────────────────────────────────────────┤
│ Served runtime (local HTTP API)              │
│  routing → tool execution → answers          │
├───────────────┬──────────────┬───────────────┤
│ Local models  │ Cloud lanes  │ Wallet (opt)  │
│ (Ollama etc.) │ (your keys)  │ pilot lanes   │
├───────────────┴──────────────┴───────────────┤
│ Records: receipts, ledgers, fault registry   │
│ Local storage (SQLite under your profile)    │
└──────────────────────────────────────────────┘
```

Принципы, которые обеспечивает код:

* **Локально по умолчанию; облако — по вашему ключу.** Облачные направления существуют только с вашими учётными данными и
  вашими потолками.
* **Один владелец у каждого решения.** У разрешений, расходов и исходящего сетевого трафика есть по одному
  контракту-владельцу; сбои классифицируются на той границе, которая ими владеет.
* **Говорить, что не удалось.** Неизвестные исходы помечаются как неизвестные; отказы говорят, что не
  произошло; закреплённая модель никогда не подменяется молча.
* **Всё записывается.** Вызовы инструментов, одобрения, платежи и обновления создают квитанции в
  вашем профиле.

## Настройка среды разработки

```bash
git clone https://github.com/Parad0x-Labs/vool.git
cd vool
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest tests -q            # the suite
```

Заметки о платформах, полное устройство инструментария и проверки перед выпуском находятся в
инженерной документации репозитория (`docs/` в корне репозитория; глубокие внутренние подробности не входят в этот публичный
сайт документации).

## Документация: один канонический источник

Эта документация создаётся из **одного** источника — папки `docs/` этого репозитория (структура
GitBook, `.gitbook.yaml` в корне репозитория). Из неё собирается публичный сайт документации. Чтобы работать с документацией:

```bash
python3 tools/docs/build_docs.py --src . --out docs-build --base /docs
python3 tools/docs/check_docs_build.py docs-build /docs
python3 -m http.server -d docs-build 8000   # local preview
```

Справочник ошибок (`ERROR_BOOK.md`) и манифест передачи на локализацию
**генерируются из собственных реестров среды выполнения** — генерируйте их заново и никогда не правьте вручную:

```bash
python -m tools.generate_error_book
python -m tools.generate_localization_handoff
```

Отдельный тест проваливает сборку, если сгенерированные файлы расходятся со своими реестрами.

## Участие в разработке

* Небольшие изменения с ревью; каждое утверждение в документации должно соответствовать коду в том виде, в каком он выпущен.
* Сохраняйте стабильные коды и идентификаторы — они живут дольше сборок.
* Никогда не расширяйте полномочия молча: новое разрешение, новый путь расходов или новое направление исходящего трафика — это изменение
  архитектуры, а не заплатка.
* Ограничения бета-версии документируются, а не скрываются — если вы нашли недокументированное ограничение, это
  ошибка в документации.
