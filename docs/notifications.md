# Notifications and model discovery

The header bell is the inbox for VOOL alerts. It has one persistent unread count shared by windows and retained across restart.

| Section | What appears |
| --- | --- |
| Needs you | Reminders, calendar alerts, approval requests, failed chat runs, and watched-model price increases or delistings. |
| Updates | Completed or stopped chat runs and other catalog changes, including observed free models that have not qualified for discovery. |
| Model offers | Qualified model offers. |

Opening a section marks the displayed items read. Other sections and later arrivals remain unread. Dismiss hides that inbox item; it does not approve an action, change the selected model, stop a job, or disable future reminders.

Model → **Discover models** stays available even when no offer has qualified. Its evidence cards retain component prices, capabilities, provider terms, offer limits, timestamps and sources. **Try once** and **Set as default** use the existing model-selection and spending gates. Opening discovery never changes the selected model.

**Hide offer** explicitly removes a recommendation and its corresponding inbox alert. Dismissing just the inbox alert leaves the recommendation available in discovery.

Matching catalog and qualified offer observations share one notification. A later qualification can enrich that notification without resetting its read or dismissal state. Distinct price changes and expiring offers retain separate identities. Initial catalog history is listed as read rather than replayed as new alerts; the previous browser inbox state is imported once.

Run notifications come from stored runtime events, not text generated by a model or the browser. A run completed in the currently displayed chat is acknowledged when the browser receives that completion. Background completions remain available after the window reloads. Calendar and reminder detail cards keep their snooze, meeting, policy and chat links. macOS delivery remains an independently enabled channel; model offers do not start sending OS alerts.

The inbox lists up to 200 current items per request; model discovery retains its existing bounded recent-finding view. Provider evidence and model eligibility still come from their existing authorities.
